# 停车位历史趋势

## 功能与边界

停车卡片增加“查看历史趋势 / 热力条”入口（新版 `commuteV2` 和旧版
`commute` 都支持）。可切换 B25 / 中盟、选择日期、点击“上周此日”。
曲线横轴为北京时间、纵轴为剩余车位；热力条可点击查看数值。灰色表示没有采样，
红色表示实际观测为零，缺失的采样不连线。图中虚线标记当前北京时间，
“当前时段”展示该日期对应采样槽的观测，不是对当前余量的预测。

不会改变现有实时余量刷新、缓存、滚动数字或 `parking-full` 停满时间功能。
既有 `parking-full` 仅记录阈值/停满时间，不能还原完整余量历史。
**新历史只会从启用定时器之后开始累积，没有部署前的完整历史。**

## 调用链

```text
腾讯云定时器 parking-history-collect
  → cloudfunctions/parkingHistory/index.js
  → history.js: createHandler / 采集分支
  → source.js: fetchSpaces / parseSpaces
  → 同现有实时功能的 ParkingSpaceApi/GetData（一次请求提取两处余量）
  → 当前 CloudBase 环境的 parking-history 集合

停车卡片 toParkingHistory
  → pages/router.js: navigateToParkingHistory
  → pages/home/parkinghistory/parkinghistory.js: loadHistory
  → repository/dashboardRepo.js: fetchParkingHistory
  → repository/baseRepo.js: cloudFunctionCall
  → parkingHistory 云函数 action=history（仅查询数据库，不访问上游）
  → model.js + canvas 曲线 + WXML 热力条

独立每日定时器 parking-history-cleanup
  → 同一云函数的清理分支
  → 仅删除 parking-history 中早于保留边界的记录
```

云函数用 `cloud.DYNAMIC_CURRENT_ENV`，客户端继续使用 `miniprogram/app.js`
已有的环境选择。**数据存在这个腾讯 CloudBase 环境的云数据库中，不是小程序
本地缓存、仓库文件或服务器磁盘，也不需要新建数据库服务。**
开发者须确认 fork 使用自己的测试环境，不要直接部署进他人的现有环境。

## 存储形状与成本

新增专用集合名固定为 `parking-history`，一条文档合并两个停车场：

```json
{
  "_id": "2026-10-26-540",
  "date": "2026-10-26",
  "minute": 540,
  "sampledAt": 1792976400000,
  "intervalMinutes": 10,
  "b25": 123,
  "zhongmeng": 45
}
```

这是形状示例，不是实测数据。`date`、`minute` 是北京时间的日期和当日分钟数；
`sampledAt` 是请求返回后的 Unix 毫秒时间戳。ID 固定为“日期-采样槽”，
同槽重试覆盖同一文档，避免重复增长；保存实际采样间隔，以便后续调整间隔时识别曲线缺口。
接口只返回图表所需字段，不暴露数据库 ID。

默认每天最多 12 小时 × 6 = **72 条**，两个停车场不会翻倍。
每周五个工作日为 360 条；八个连续自然日最多六个工作日，正常清理后最多约
**432 条**。按每条逻辑载荷约 200–500 字节粗估约 86–216 KB；
数据库元数据、索引、计费单位、日志和失败积压另计，不能视作账单保证。
若扩大到全天、保留期 31 天，成本会相应增加。

采集定时器每十分钟全天触发（144 次/日），函数先在内存判断工作日、日期、
时间窗和间隔；不符合条件时**不请求上游，也不读写数据库**。
清理每天触发一次，因此默认每 30 天约 4,350 次函数调用，实际有源请求仅工作日
时间窗内最多 72 次/日；这是以少量空调用换取只修改 JS 即可调整时间窗的简化方案。
定时器平台重试可能额外请求上游，但不会新增重复文档。

## 配置与修改

修改 `cloudfunctions/parkingHistory/config.js` 后重新部署该云函数：

| 配置 | 默认 | 约束 / 含义 |
| --- | --- | --- |
| `intervalMinutes` | `10` | 允许 `10`、`20`、`30`、`60`，与十分钟基础触发器对齐 |
| `startHour` | `7` | 北京时间整点，包含起点 |
| `endHour` | `19` | 北京时间整点，不含终点，最大 `24` |
| `retentionDays` | `8` | 含今天，允许 8–31 个自然日 |
| `skipDates` | `[]` | 北京日期字符串数组，例如 `['2026-10-01', '2026-10-02']` |

时区固定为 **Asia/Shanghai / UTC+08:00**：`history.js` 和前端 `model.js`
使用 UTC 算法加固定八小时偏移，不依赖客户端所在地或服务器本地时区。
苏州没有夏令时；本功能不扩展成通用跨时区调度系统。

周六、周日一律不采样。**节假日不自动识别**：部署者需维护 `skipDates`，
留空就不会额外跳过工作日假期。此方案不依赖公共节假日 API，也不自动处理调休：
即使某个周末是补班日，仍跳过。修改节假日配置后只需重部署函数代码。

为何保留八天而不是七天：今天 D 与 D−1…D−7 一共八个自然日，
只有这样才能在今天查看上周同一日。默认日期选择器覆盖这八天；
保留期加长后，查询返回的 `earliest` 会相应扩展。
缩短保留期前应确认可接受不可逆的数据删除，必要时由环境所有者先导出备份。

`cloudfunctions/parkingHistory/config.json` 定义两个独立定时器：

- `parking-history-collect`：`0 */10 * * * * *`，每十分钟。
- `parking-history-cleanup`：`0 5 0 * * * *`，平台调度时区的每天 00:05。

七字段格式沿用仓库 `cloudfunctions/luckDraw/config.json` 的模式。
部署后必须在控制台核对其实际启用状态、表达式及平台时区，
建议使用北京时间。每十分钟触发不受整小时时区偏移影响；
清理始终按执行当时的北京时间计算边界，不依赖调度器的日历日期。
不要只修改控制台而让仓库配置失真。当前支持的采样间隔无需修改基础触发器；
如需要低于十分钟，必须同时修改校验、触发器和成本估算，不是直接填 `1`。

## 清理与安全边界

以执行时北京时间日期 D 为准，仅选择
`date < D − (retentionDays − 1)` 的新集合文档；边界当天完整保留。
即使周末、假期或关闭采集，独立每日清理仍可运行。
每批最多 100 条，至多五批，即每次最多 500 次定向删除；
到达上限记录 warning，后续每日调用继续清理。默认每日过期量最多 72 条。
修改为更大窗口/更短保留期可能产生积压，应监控而不是无限循环删除。

**逻辑查询窗口有界，不等于保证到期时物理立即删除。**
停用定时器、平台故障、索引/权限错误或删除失败都可能延迟物理清理；
查询仍拒绝窗口外日期。错误向平台抛出并写日志，不转换成成功。
部署者应为云函数失败和清理上限 warning 配置监控/告警，并核查数据库存量。
无法声称仅凭本代码就能保证硬性存储上限。

采集/清理只接受 Timer 事件、两个固定 TriggerName，且拒绝 SDK 返回的
客户端 OPENID / APPID / UNIONID 或非服务端调用 SOURCE。
**客户端传入 Type/TriggerName 不能代替可信调用身份**；身份取自 SDK，
不从 event 取。云端服务账号/控制台管理员属于信任边界，应使用最小 IAM 权限。
不应开放无认证 HTTP 云函数入口，也不应设置伪造或清空调用身份的网关。
上线时需实际确认 Timer 的身份上下文可通过校验，并验证小程序伪造事件被拒绝。

集合设置为“所有用户不可读写”（客户端权限规则为 `read: false`、
`write: false`），由云函数服务端访问；历史通过只读 action 提供。
集合名固定，查询只接受严格格式的保留期内日期，调用方不能指定集合、
删除条件或任意查询。新增清理**不读写或删除**已有 `parking-full`、用户数据等集合。
SDK 的服务端权限可绕过客户端规则，因此代码审查和 IAM 权限仍然重要。

上游响应必须同时包含两处非负整数余量，缺项、重复项、格式错误、HTTP 非 200、
8 秒超时或过大的响应都会失败，不会写入“0”冒充有效数据。
沿用现有公开 HTTP 地址，没有引入新外部服务；链路本身不提供 TLS 完整性保障。
不进行历史回填或自动高频重试。

## 部署顺序（需要环境所有者执行）

1. 在微信开发者工具选择**自己有权限的测试 CloudBase 环境**，核对客户端
   `miniprogram/app.js` 的环境与部署目标一致。
2. 新建集合 `parking-history`，禁止客户端直接读写；创建复合索引
   `date` 升序 + `minute` 升序，并确保日期范围清理查询有可用索引
   （必要时另建 `date` 升序索引）。不要更改旧集合权限。
3. 编辑 `config.js` 的节假日、时间窗和保留期；上传部署 `parkingHistory`，
   由云端安装依赖。使用 Node.js 16 或更新的受支持运行时，建议 Node.js 18+；
   云函数超时建议 60 秒，预留最多 500 次删除的时间。
   本地 Node.js 测试使用 22，无需为图表引入 npm 依赖。
4. 安装并启用 `config.json` 两个触发器；不要假设仅上传代码就已部署触发器。
   在控制台核验触发器名称和时区，不能改名后仍沿用旧处理代码。
5. 在工作日时间窗内观察真实定时触发，确认日志、两个余量和文档 ID；
   在测试环境验证客户端伪造 Timer 请求被拒绝。使用合成过期数据核查
   清理边界与日常清理日志。不要用生产集合做删除实验。
6. 编译小程序并发布体验版：检查两版入口、日期选择、B25/中盟切换、
   上周同日、零余量、无记录、失败重试、缺口曲线、热力条点击、
   小屏布局以及实时卡片/停满时间无回归。确认无误后再发布正式版。

新云函数须先于客户端发布，否则历史页会显示加载失败及重试。
现有 `uploadCloudFunction.sh` 含旧环境/绝对路径，不是本功能的部署命令。
卸载时先停用两个触发器及入口；是否删除专用集合由环境所有者决定，
不提供批量删除其他集合的脚本。
